# Выпуск Keyra через GitHub Actions

## Как устроен процесс

Версия приложения хранится в `app-info.properties` и входит в релизный коммит.
Тег имеет вид `v0.1.0`, APK — `keyra-0.1.0.apk`. Actions проверяет совпадение
тега, исходников, рецепта F-Droid и changelog. Подмена версии только на CI не
используется: F-Droid должен получить ту же версию, собирая исходники из тега.

- **Build**: запускается при push в ветку, pull request и вручную. Проверяет
  метаданные, выполняет JVM-тесты, Android Lint и собирает неподписанный release
  APK. APK, отчёты и R8 mapping доступны в артефактах запуска. Ключ не нужен.
- **Release**: запускается при push тега `v*` или вручную для существующего тега.
  Проверяет исходники и историю версий, выполняет те же тесты и сборку, затем
  отдельным заданием подписывает APK постоянным ключом. Последнее задание
  создаёт GitHub Release с APK, `SHA256SUMS` и `release.json` с версией,
  идентификатором приложения, коммитом и отпечатком сертификата.
- Release Notes формируются из двух файлов
  `fastlane/metadata/android/{ru-RU,en-US}/changelogs/<versionCode>.txt`.
  Имя файла — **Android versionCode**, а не `versionName`.

Публикация автоматическая. Сначала создаётся черновик, в него загружаются все
файлы, затем он становится публичным. Если загрузка прервётся, повторный запуск
может продолжить черновик. Опубликованный Release не перезаписывается: исправления
выпускаются новой версией. Не передвигайте уже выпущенные теги.

Сейчас поддерживается одна последовательность стабильных версий `MAJOR.MINOR.PATCH`:
без суффиксов `beta`/`rc`. Новая версия и её versionCode должны быть больше всех
существующих стабильных тегов. Actions читает versionCode прежних тегов из
`app-info.properties`; старый тег без этого файла потребует отдельной миграции.

## Однократная настройка GitHub

1. Отправьте workflows и скрипты в репозиторий. Для ручного запуска workflow
   должен присутствовать в основной ветке репозитория.
2. В **Settings → Secrets and variables → Actions → New repository secret**
   добавьте четыре секрета:

   | Secret | Значение |
   | --- | --- |
   | `ANDROID_KEYSTORE_BASE64` | Существующий постоянный keystore, закодированный в Base64 |
   | `ANDROID_KEYSTORE_PASSWORD` | Пароль keystore |
   | `ANDROID_KEY_ALIAS` | Alias ключа внутри keystore |
   | `ANDROID_KEY_PASSWORD` | Пароль ключа; если он совпадает с паролем keystore, укажите его ещё раз |

   На своём компьютере можно скопировать Base64 в буфер обмена PowerShell,
   подставив путь к **своему существующему** ключу:

   ```powershell
   [Convert]::ToBase64String([IO.File]::ReadAllBytes('C:\path\to\keyra.jks')) | Set-Clipboard
   ```

   Вставьте результат прямо в GitHub Secret. Base64 — кодирование, а не
   шифрование: не добавляйте его в Git, issue или обычную переменную Actions.
   Пароли и ключ не нужно передавать в чат. Сохраните отдельную резервную копию
   keystore и паролей: GitHub Secrets не заменяет её.
3. Используйте ключ с SHA-256 сертификата
   `c534c1fa0403986e4a61c24fef8ebdfc0625ca0b991ec765ae6354ec4fed8cea`, уже
   указанным в рецепте F-Droid. Задание подписи сверяет этот отпечаток и
   останавливается при несовпадении. Новый случайный ключ создавать не нужно.
4. GitHub Actions должен быть разрешён в настройках репозитория. Workflow сам
   запрашивает `contents: write` только для задания публикации; отдельный PAT не
   требуется. Политика организации, если она есть, должна разрешать этот доступ.

Ключ доступен только шагу подписи после выполнения Gradle. Он восстанавливается
во временный файл и удаляется при выходе из шага. Pull request и обычная сборка
ветки не используют секреты подписи. Все сторонние Actions закреплены по commit SHA.

## Первый релиз 0.1.0

Версия `0.1.0`, code `1` и оба changelog уже подготовлены. После настройки
секретов, проверки текста и успешного **Build** закоммитьте изменения, затем:

```powershell
git tag -a v0.1.0 -m 'Keyra 0.1.0'
git push origin v0.1.0
```

Коммит с workflow и всеми релизными файлами должен быть отправлен в GitHub;
тег ставится именно на него. Отправка тега запускает **Release** автоматически.
Самостоятельно создавать Release перед этим не нужно.

## Следующие версии

Node.js 22 или новее достаточно; npm-пакеты для команды подготовки не нужны.
Например, для версии `0.1.1`:

```powershell
node scripts/release.cjs prepare 0.1.1
```

Команда:

1. Обновит `application.version.name` и увеличит `application.version.code`
   на единицу. При необходимости можно явно указать больший code:
   `node scripts/release.cjs prepare 0.1.1 --code 10`.
2. Добавит build entry для нового тега в локальный рецепт F-Droid, сохранив
   старые записи, и обновит `CurrentVersion`/`CurrentVersionCode`.
3. Создаст оба changelog с отметкой TODO. Заполните их реальными изменениями
   на соответствующих языках, не более 500 символов каждый. Проверка не
   пропустит пустые, отсутствующие, слишком длинные файлы и отметки TODO.

Она не создаёт коммит или тег. Повторный запуск с текущей версией не увеличивает
code и не затирает уже заполненные changelog. Уменьшение версии и повторное
использование code для новой версии запрещены.

После редактирования:

```powershell
node scripts/release.cjs check
git diff
# Закоммитьте и отправьте исходники вместе с обновлёнными релизными файлами.
git tag -a v0.1.1 -m 'Keyra 0.1.1'
git push origin v0.1.1
```

Вручную редактировать несколько файлов версии не нужно. Автоматизация
происходит **до создания тега**, а Actions собирает уже зафиксированный
релизный коммит. Release Notes отдельно дублировать не требуется.

## Ручной запуск и ошибки

В **Actions → Release → Run workflow** выберите основную ветку и укажите,
например, `v0.1.0` в поле `tag`. Workflow соберёт commit этого существующего
тега. Имя ветки вместо тега, несовпадение версии или отсутствие changelog
приведут к ошибке. Можно также использовать **Re-run failed jobs**, например
после добавления недостающего секрета.

Если ошибка в исходниках, обновите их и подготовьте новую версию. Если проблема
только в настройке секретов или загрузке файлов и Release ещё не опубликован,
повторите запуск для того же тега. Неподписанный APK из **Build** нельзя
установить как обычный релиз; устанавливаемый APK находится в GitHub Release.

Отчёты обычных сборок хранятся 30 дней, релизные отчёты/R8 mapping — 90 дней,
подписанный артефакт workflow — 30 дней. Файлы опубликованного GitHub Release
не зависят от срока хранения артефактов Actions. При необходимости сохраните
mapping долговременно отдельно.

## Связь с F-Droid

Linux CI использует JDK 17, Gradle 8.11.1 из wrapper, платформу Android 36 и
Build Tools 35.0.0. Gradle собирает неподписанный APK из неизменённых исходников;
`apksigner` добавляет v2-подпись отдельным шагом. Опубликованный адрес
`releases/download/v<version>/keyra-<version>.apk` совпадает с `Binaries` рецепта.

GitHub Actions не отправляет приложение в F-Droid и не доказывает
воспроизводимость в его buildserver. Нужны проверки и подача рецепта по
[инструкции F-Droid](fdroid/README.md). Обновление локального рецепта командой
подготовки также не обновляет автоматически отдельный репозиторий `fdroiddata`.

Проверки workflow: тесты скрипта подготовки, структурная проверка YAML/метаданных,
provenance иконок, JVM-тесты приложения/core, Android Lint и release-сборка.
Эмуляторные UI-тесты и нативный F-Droid scanner в этот процесс не включены.
